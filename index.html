About me

I write and maintain documentation for healthcare and data privacy software. Most of it is user guides, technical and installation guides, and release notes, written in MadCap Flare.

Each update starts with what engineering gives me: the Jira ticket, the test plan, a demo recording, comments from developers, and the guide as it reads today. I work out what the reader needs to know or do, write only what those sources back up, and then make the change in Flare for review.

I use AI tools, mainly Cursor, to speed up the reading and comparing. They don't decide what goes into a guide. I do, and nothing is edited until it has been approved.

What I do

  • User guides. Step-by-step procedures, prerequisites and cautions, written around what the user sees on screen.
  • Technical and installation guides. Configuration, environments and setup, with a clear line between what is supported and what isn't.
  • Release notes. Short summaries of what changed, without implementation detail the reader doesn't need.
  • Working from sources. Going through tickets, acceptance criteria, test plans and demos to find out what needs to change in the docs.
  • Review packages. A handoff that shows reviewers what changed, where it came from, what I checked and what is still open.
  • AI-assisted drafting. Cursor for pulling information out of sources, comparing it with the current guide and writing a first draft. I approve every edit.

Work

These are the three products I document. I've left out confidential procedures and internal figures.

PET

User guide and release notes for a privacy treatment product

With each release, I turned the changes into tasks that dataset owners, operators and administrators could follow, and wrote short release notes. I worked from Jira, test plans and demo transcripts, and compared each change with the current user guide topic before editing it. I added screenshots only when a step depended on them. API and implementation details went into the technical guide, or were left out if they didn't help the reader.

Topics I covered include the dataset lifecycle (viewing, approving and deleting a draft dataset), privacy treatments and their settings, and administration: tenants, domains, roles and app clients. I also wrote the release notes on enabling and disabling accounts.

Eclipse

Installation guide and technical guide for a data anonymization platform

Cloud and configuration changes are easy to over-document, so I stuck to what installers need: the setup that works, options that aren't supported, and settings that no longer apply. I traced every change back to its ticket and the engineering comments, and updated topics and the table of contents only where something had changed. When there was no test plan or demo, I said so in the review package instead of guessing.

I wrote the AWS installation topics for EMR, EMR Serverless, Databricks and Spark, including a new integration topic that didn't exist before, and added notes on settings that don't apply on certain platforms.

NextGen Tokenization

User guide, technical guide and release notes for a tokenization product

People using this product need to know two things: how to run it, and how matching, tokens and deployment settings work. I look after the user guide from getting started through projects, job runs and troubleshooting, plus the reference sections on tokens, confidence scores and job parameters. For the technical guide, I checked the existing deployment topics first and added only what was missing, based on what the ticket covered.

Here is how I split the content:

  • User guide: getting started, projects, column settings, starting a run, how runs are queued, and what to do when a message appears.
  • Reference: how tokens are built, how confidence scores are calculated, how the match threshold works, and which job parameters to set.
  • Technical guide: environment variables and deployment setup.

If a topic is already correct, I leave it alone. I add a sentence only when the ticket, a deployment note or the guide itself shows something is missing.

How I handle a release

With three products, several guide types and a long list of tickets each release, I needed a process I could repeat. I follow the same steps every time and make a decision at each one before moving on.

  1. Pick the release and check that the sources are available.
  2. Pull the Jira tickets, Confluence test plans and demo transcripts, and note anything missing.
  3. Decide which guide the change belongs in (user, technical, installation, release notes, or none) before drafting.
  4. Write up the change and check it against the style guide.
  5. Share the exact wording for approval. I edit Flare only after that.
  6. Check for gaps, update Flare, build the PDF if needed, and send the review package.

AI helps with steps 2 to 4: pulling information out, comparing it with the current topic, and writing a first draft. I decide the scope, remove anything the sources don't support, and approve the final text.

Every review package lists the sources I used (and any that weren't available), which guide the change went into, and what I checked, including anything still waiting on a subject matter expert.

One thing I'm strict about: an AI suggestion or a screenshot doesn't prove how the product behaves. Code can confirm a label on screen, but I need the ticket, the test plan or an engineer to confirm how a feature works.
